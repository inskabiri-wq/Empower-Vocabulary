# 2026-08-19 - Six reported items

## 1. Tiles appeared then disappeared
hub.js rendered the full grid on DOMContentLoaded using
`window.featureToggles || {}`. An empty object reads as "everything is active",
so all 8 tiles painted; a moment later the real toggles arrived and it
re-rendered, REMOVING the deactivated ones. That is the flash.

It now renders SKELETONS until the toggles actually land, then draws the real
grid once - so the first grid a student sees is already the correct one.
A 3s safety net covers the case where feature-toggles.js never loads at all
(it already fires its event even when the READ fails).

Verified with a MutationObserver over the grid: switching two skills off
produced ONE mutation, and the deactivated tiles were never present in any
observed state.

### The console messages in the screenshot
- "Password field is not contained in a form" - a Chrome hint, not an error.
  Password inputs outside a <form> stop the browser password manager working
  properly. Real, worth fixing, but it is a markup change on the login page and
  was not part of this batch.
- "apple-mobile-web-app-capable is deprecated" - fixed. The standard
  `mobile-web-app-capable` is now emitted alongside it on all 4 pages that had
  it. The apple- form is kept because iOS still reads it.

## 2. Favicon and FSM logo everywhere
- The favicon is now the Lingualab mark on 29 pages. 23 had an existing icon
  link and got the SVG inserted BEFORE it; browsers prefer SVG and fall back to
  the .ico only if they cannot render it.
- 6 pages had NO icon link at all - including BOTH dashboards - so they were
  falling back to /favicon.ico by browser default and still showed the old mark.
  They now declare it explicitly.
- manifest.json gets the SVG as an "any"-size icon, so the installed PWA picks
  it up. The PNGs stay as fallback.
- The login and reset-password pages showed fsm-logo.png beside the wordmark;
  that is app chrome, so it is the mark now.
- fsm-logo.png and fsmvu-seal.png REMAIN on the certificate. A certificate
  carries the university's marks, not the app's logo.

## 3. "Save Profile" was invisible
`.save-profile-btn` uses `background: var(--accent-gradient)` with white text.
`--accent-gradient` is defined for index, classroom, teacher and app.html - but
NEVER for the student side, while student/css/extra.css uses it FOUR times. An
undefined custom property makes the whole declaration invalid, so the button
painted no background: white text on white. Defined it for both student themes.

## 4. Deactivated skills still offered in assignments
`SKILL_REGISTRY.active()` filtered on `status === 'active'` - a readiness flag
hardcoded in the registry - and knew nothing about the org toggles. So a skill
an admin switched off vanished from the hub but still appeared in the
assignments skill strip and creation flow. Same switch, two answers.
It now also requires `featureToggles[id] !== false`. One choke point, so every
consumer is fixed at once. Verified: with speaking+writing off, active() returns
vocabulary / listening / reading / grammar only.

## 5. Student data moved into the profile box
Class / level / module / year describe the STUDENT, not their assignments, so
the chips moved from the Assignments card into the Profile box.
MOVED, not copied: auth.js writes into them by id, and duplicating the ids would
send updates to whichever element the browser returned first. Verified each id
appears exactly once and the div count still balances (328/328).

## A recurring mistake, now guarded
Semantic colours were flattened to blue for the THIRD time, because the sweep
maps amber to blue unconditionally and re-running it undoes the previous
restore. 19 lines restored exactly from the pre-sweep backup, and the sweeper
now skips any line naming a meaning (warning/error/success/correct/overdue).
One caveat found immediately: the guard is line-based, so a single line
declaring `--cyan` AND `--amber` together was skipped entirely. Fixed by hand.
